日期：2026-10-14。用户新建真实歌单，并明确授权收藏/取消收藏、临时歌单创建/修改/删除和会员完整播放测试。每日推荐按用户要求暂不继续。

## 本人歌单：验证成功

- 本人收藏分类接口请求 contentTypes=[1,4,5,7]，limit=999，返回 960 条歌曲及 1 条 type=5 自建歌单。
- 使用该歌单返回的真实 contentID 请求 playlist/detail/all 的 playListID，成功返回详情和 5 首歌曲。
- 只读用户新建歌单，没有修改它。
- 同路径 limit=1000 返回 HTTP 400，999 成功；只确认这两个值的表现，不把 999 说成完整文档定义的最大值。

## 收藏写操作：验证成功且恢复

1. 选择搜索结果中的一首歌曲，确认不在基线收藏集合。
2. favorite/simple/exist 返回 exist=0。
3. favorite/create 返回 000000。
4. 再读 exist=1，证明不是只收到成功响应。
5. favorite/delete 返回 000000。
6. 再读 exist=0，恢复测试前状态。

## 自建歌单写操作：验证成功且清理

- 创建带唯一临时名称的歌单，shareFlag=0，包含一首测试歌曲，返回新 playListID。
- 读取临时歌单详情成功。
- playlist/update：actionType=1 修改 listDesc（简介），返回 000000；重新读取确认新简介确实存在。
- 本轮验证的是简介修改，不宣称已验证改名、排序、封面或增删歌单内歌曲。
- 首次误用 favorite/delete 删除 type=5，虽然返回 000000，歌单仍在；favorite/simple/exist 对 type=5 返回 110020（不支持）。没有据此宣布清理成功。
- 改用 POST /music-userbehavior-service/v1/service/playlist/delete，JSON {playListID:本次创建返回的ID}，成功删除。
- 最终重新读取音乐库，歌曲/歌单 ID 集合与基线比较：added=0、removed=0，临时歌单不再存在。
- 不能承诺服务端操作日志/同步时间完全无变化，但用户可见音乐库的成员集合已恢复；未修改用户已有歌单。
